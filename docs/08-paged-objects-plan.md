# Paged Objects — Implementation Plan

> Companion to [08-paged-objects.md](08-paged-objects.md), which is the design of record; section references (§) point there. This plan covers **v1: hash only, EloqStore only** (§11 Gating, §13 Store handler changes). It sequences the work, names the dependency edges, and sets per-phase test gates. It restates no design — when this plan and the design doc disagree, the design doc wins.

## Ground rules

- **Two repos, strict PR order.** Engine work lands in `data_substrate` (repo `eloqdata/tx_service`) first; the parent repo bumps the submodule pointer and layers protocol work on top. Squash-merge, rewrite the squash message per repo policy. Each phase below is 1–3 PRs; a phase's engine PR always precedes its eloqkv PR.
- **Gating.** A temporary compile macro (working name `ELOQKV_PAGED_OBJECTS`) keeps half-finished code out of shipped binaries; CI builds both settings from the first PR that introduces it, and the macro is deleted in Phase 8 (§11). The runtime conversion-threshold knob defaults to *disabled*, so every phase ships dark.
  - **The macro gates creation only.** It acts on `GetPagedConvertThreshold()`, which returns 0 when the macro is off; `RedisEloqObject::DeserializeObject` compiles the `PagedHash`/`TTLPagedHash` cases unconditionally, per §11's rule that the ability to *read* a converted object is permanent. Guarding the read side instead is not a stricter version of the same idea, it is a data-loss bug: nothing else in the layer was conditional, so an "off" build still converted objects and checkpointed `PagedHash` rows, then aborted in `DeserializeObject` the first time it read its own store back. That is exactly what happened on the `bld-eloqstore` tree, and it is why the standby bring-up measured a non-paged binary for a full round of tests.
- **Test harness inventory** (referenced by the phase gates): protocol-layer unit tests (new, gtest/ctest in eloqkv), engine Catch2 tests (`data_substrate/tx_service/tests/`), the TCL suite (`tests/unit/eloq/hash.tcl` run with the threshold forced to a few KB so every hash pages), the #509 differential-replay harness (§15.1), and Debug-build fault injection (`WITH_FAULT_INJECT`) for crash/interleaving matrices.
- **Byte-stable metadata serialization is an implementation requirement even though the design doesn't demand it**: serialize `page_entry_counts_` in directory order, not map iteration order. The §16 testing emphasis ("replay, assert identical layout") diffs serialized metadata byte-for-byte, and map-order serialization would make identical layouts compare unequal.

## Phase 0 — Wet cement and confirmations

Everything in §5 that becomes unchangeable once a byte hits a store, plus the two design assumptions the doc flags as needing confirmation from their owners. Cheap to build, expensive to get wrong, and it unblocks both repos.

**data_substrate:**
- The composite page `TxKey` (`<object key, page id>`, `Hash()` = object key's hash) and the **single shared key encoder** for `\x00EKVPAGE<object key><kind><page_id BE>` (§5, §13 "Key derivation needs one shared encoder").
- ~~Confirmation A~~ **RESOLVED (2026-07)**: the fetch-before-lock ordering at `object_cc_map.h:310-315` carries no correctness requirement — it exists to reduce lock contention. Deferring acquisition past `ExecuteOn` is safe (§6, recorded there). Phase 3 is unblocked.
- ~~Confirmation B~~ **RESOLVED (2026-07)**: EloqStore `BatchWriteRecords` is all-or-nothing, and batch size has no hard upper bound — oversized batches are written, never rejected or chunked (§13, recorded there). Phase 2b is unblocked. Still open from this bullet: §15.4 (does EloqStore expose a prefix/range delete) — informs the sweeper only, nothing in v1.

**eloqkv:**
- Append the two `RedisObjectType` tags (paged hash, paged hash + TTL) with `DeserializeObject` dispatch stubs (§5).
- **Reserved-prefix rejection**: `ExecuteCommand` next to `MAX_KEY_SIZE`, plus the `RESTORE`/RDB-import paths (§5). Ship this immediately — it is independently valuable, zero-risk, and must be in production *before* any paged row can exist.
- Pin the constants under format version 1: MurmurHash3_x64_128 seed, metadata layout, page-size flag (default 128 KB), conversion-threshold flag (default disabled), whole-object reply bound (§3), TTL slack `S` (§9).
- Introduce the compile macro + both-settings CI.

**Exit criteria:** prefix rejection live in a release; encoder round-trip unit tests (encode/peel, namespace-prefixed keys); both confirmations answered in writing (doc updated if either surprises).

## Phase 1 — Paged hash core, in-memory only (eloqkv)

Pure library code with no engine dependency: `PageView` over the sorted slotted page (find/insert/erase/compact/`SplitInto`), the extendible directory with deterministic splits and the `count == 65535` valve, `PagedHashMetadata` codec, large-value runs, `free_ranges_`/`pending_delete_` interval logic, `PageBuf` via aligned mimalloc allocation, `RedisPagedHashObject` skeleton (`pages_`, `tx_contexts_`, `MemUsage`/`SerializedLength`/`LogicalBytes` split — mind the §4 rename hazard).

**Tests (the cheapest place to nail §16's structural invariants):**
- Split determinism: same directory + contents ⇒ byte-identical split, property-tested across random workloads.
- Contiguous-partition property of splits; valve behavior at oversized page configs.
- Canonical interval set invariants for `free_ranges_`; append-only/prefix-drain/never-coalesce for `pending_delete_`; the four-state id lifecycle.
- Metadata codec round-trip + byte-stability (directory-order counts).
- Layout-diff harness: apply a command trace twice, assert identical serialized metadata + pages — this becomes the engine-independent half of the §15.1 audit and the §16 replay test.

**Exit criteria:** all above green; ASAN/UBSAN clean; a fuzz pass over `PageView` mutations.

## Phase 2 — Fetch and flush plumbing (data_substrate)

The engine learns to read and write paged objects, **without** the Yield protocol — exercised via a test-only fixture that installs a synthetic paged payload (command overrides don't exist yet).

**2a — fetch:** `PageFetch : FetchRecordCc` with its own `Execute()` override; `FetchHub` on `KeyGapLockAndExtraData` (`IsEmpty`/`Reset`/`ClearTx` integration, the `pin_count_` rename); `DeserializeCurrentPayload` virtual + `BackFill` page mode (skip `SetCommitTsPayloadStatus`; missing live row ⇒ corruption error to waiters) (§13).

**2b — flush:** `PagedObjectFlush` variant; `ExportForCkpt` one-indivisible-record; DSS client 1+N row expansion; **record-boundary batch cutting** in `PreparePartitionBatches`; post-flush callback (guarded `flushed_` bit, `pending_delete_` prefix drain); `records_ttl` = deadline+S on the metadata row, 0 on page rows (§9, §13).

**Tests:** Catch2 round-trip: synthetic paged object → checkpoint → evict → fault pages back → identical bytes. Batch-boundary property test (an object never splits across batches; oversized objects write). Post-flush guard races (page dirtied mid-flush stays dirty). Corruption-error path. TTL attribute placement per row kind.

**Exit criteria:** round-trip green against a real EloqStore instance; crash injection between export and callback shows no `flushed_`/`pending_delete_` corruption.

## Phase 3 — The Yield protocol (data_substrate) — highest risk, smallest possible PR

`ExecResult::Yield` + `ExecuteOn` fetch context (contract change is EloqKV-only, §13); `BlockOnPageFault` with its three resume paths (speculative, lock-held, routing re-check); **deferred acquisition + the grantability test** — note this is a *correctness* item, not an optimization: it is what makes "never release a lock on I/O error" a safe blanket rule, because a fault can then only occur holding nothing, or holding a lock the transaction already recorded (§6); `result_` reset on authoritative re-runs; `TxPageContext` lifecycle including `PostWriteCc` release by tx number and the `kDrainTxn` sentinel skeleton; the §7 swap rule (hub splice + context erasure + eager wake) wired into every payload-install site; the §8 allocation-pressure throttle (`EnqueueWaitListIfMemoryFull` on the fault path).

**Sequencing inside `ApplyCc`** (the grantability test replaces the conventional acquisition *in place*, and its verdict is consumed after execution):

1. scope check — paged and not fully resident, else today's sequence unchanged;
2. **grantability test → flag**, sitting exactly where the conventional lock step sits, taking nothing;
3. TTL check and dirty-payload creation, keeping their position relative to `ExecuteOn`;
4. `ExecuteOn` (may yield);
5. consume the flag: `Yield` → park holding nothing; completed + grantable → acquire (cannot fail); completed + would-block → acquire blocking, then **re-run `ExecuteOn` and reset `result_`**.

**Code map for the inversion** (verified 2026-07, `object_cc_map.h`; line numbers drift, so search the anchors):

- `ObjectCcMap::Execute(ApplyCc&)` spans ~113–1354. The first-time path is the block `if (cce_addr.ExtractCce() == nullptr)` (~439), which locates the cce, may fetch the whole record, and then acquires at **~631** (`AcquireCceKeyLock(cce, cce->CommitTs(), ccp, RecordStatus::Normal, &req, …, cc_op, …)`). That call site is where the grantability test goes instead, on the paged path.
- The resume path's second acquisition is `LockHandleForResumedRequest` (~320) for `BlockOnRead`/`BlockOnWriteLock`/`BlockOnCondition`; `BlockOnPageFault` deliberately does not go through it (it releases the parking pin and re-runs).
- `err_code` handling immediately after acquisition (~645+) sets `obj_result.lock_acquired_` and `cce_addr.SetCceLock(...)`. The deferred path must perform both at its *later* acquisition, or the txm never learns it holds the lock.
- **Speculative-run hazard:** the write path materializes a dirty payload for a missing object at ~991–1002 (`SetDirtyPayload`, `SetDirtyPayloadStatus`, `SetPendingCmd`). §6 requires a speculative run to mutate no `CcEntry` state; scoping the deferred path to *existing paged* objects avoids it, since a non-existent object has no pages and can never fault. Add a Debug assert regardless (risk #4).
- Both write-path `ExecuteOn` sites (~1140 dirty payload, ~1182 committed payload) already handle `Yield`; the read-only sites are ~745–775. The contended re-run must reset `result_` before re-executing.

**The one test that de-risks this phase:** a property test that runs the grantability test and the real acquisition side by side across the full lattice — every `LockType`, upgrades from every held mode, queued `WriteLock` vs queued `WriteIntent` fairness — and asserts they never disagree (§6 "must mirror the real acquisition exactly"). Any divergence invalidates the atomicity argument, so this test is a merge blocker, not a nice-to-have.

**Other gates:** interleaving stress under fault injection — yield × partial eviction × concurrent faulting × term change (§16 testing emphasis); lock-held park teardown (fetch error aborts the tx and the tx abort releases the lock — no double release); speculative-run no-mutation audit (assert no `CcEntry` state change on any yielding pass); swap during park (A→B→A chained overwrites drain through one orphan list).

**Exit criteria:** monolithic paths byte-identical (the existing engine test suite must not change behavior — `BlockOnFetch`, its assert, and `fetch_record_reqs_` untouched); all new stress green for 24 h under fault injection.

- TTL-reset plain-command logging bypass at the `RecoverTTLObjectCommand()` hook for paged objects (§9).

- **The §15.1 per-command audit runs here**, command by command, with the differential-replay harness: primary trace vs `Deserialize`+`CommitOn` replay ⇒ identical layout bytes (Phase 1's harness now driven through the real engine).

**Exit criteria:** full hash TCL suite green with the threshold forced to ~4 KB (every hash pages, every command exercises the protocol) *and* with paging disabled (zero regression); differential replay green per command; `EXPIRE`/`PERSIST` on paged objects logged as plain commands and replayed correctly across a crash.

## Phase 5 — Partial eviction + memory pressure (data_substrate; parallel with 4)

Shed-clean-pages hook from `CleanPageAndReBalance`; 10 % policy over the object LRU skipping dirty/pinned; metadata-last; terminal whole-entry fall-through; severe-pressure escalation (§8).

**Tests:** shed policy unit tests (pinned/dirty exclusion, incl. `kDrainTxn` pins once Phase 6 lands); a sustained-pressure soak: bounded heap, working set ≫ budget, verify convergence (no livelock — the §6 pin-liveness argument) and that heap-usage accounting drives the loop honestly (a flush-worker-held page does not count as reclaimed).

**Exit criteria:** soak green; hot-object retention sane (fault rate on hot pages ~0 under pressure).

**Status (implemented).** Shed policy, per-object LRU, the clean-guard hook and the metadata-last terminal state are in, with `tests/unit_cc/paged_eviction_test.cpp` (7 groups; the policy claims were confirmed by fault injection — inverting the pin check, the walk direction, and the evictable-vs-resident base each fail a specific assertion). Shedding is unconditional per visit, with no pressure test of its own (§8). Confirmed firing under real pressure by breakpoint count (80 sheds at a 64 MB budget). Correctness under eviction is green whenever the workload completes: 0 mismatches across 120 × 900 and 260 × 900 field verifications. The hash TCL suite and all unit suites are green on the normal path.

**Three items remain open — this phase is NOT done:**

1. **The crash is FIXED — it was two bugs of mine, both found with the vptr detector.**

   - `PageFetch::Execute` moved itself out of the `FetchHub` into a local `unique_ptr` (so the object is destroyed as the function returns) and then returned **true**, which tells `CcShard::ProcessRequests` to call `Free()` on freed memory. It must return **false**, exactly as `FetchCatalogCc` does after erasing itself from the shard's fetch-request map. The detector named the victim outright: `victim_type=N9txservice9PageFetchE finish=1`.
   - `BackFillPage` resolved page waiters only against the **committed** payload, but a WRITE parks on the **dirty** payload (§7 copy-on-write), so its parked request lived in a different object's `tx_contexts_` and never woke. Reads were unaffected because they execute on the committed payload — which is precisely the read/write asymmetry observed (`HGET` 1 ms, `HSET` hangs forever). Fixed by installing the fetched page into, and resolving waiters against, the dirty payload as well (`PeekDirtyPayload()` added — the existing `DirtyPayload()` moves ownership out).

   With both fixes the server no longer dies under the 64 MB soak and the detector is silent.

   **The second fix is a stopgap, not the right design.** A `PageFetch` records `page_id_`, `waiter_txns_`, `cce_` and `orphaned_` — nothing that says WHICH payload it was issued against — so the completion path now probes the committed payload and then the dirty one. Two ways that is wrong: (a) the dirty payload is a COW copy that can free and reallocate page ids, and `InstallPage` guards only with `IsLive(id)`, which is true for a REALLOCATED id, so durable bytes could overwrite different content; (b) the dirty payload can vanish between issue and completion (abort, or promotion by PostWriteCc), so peeking at completion time may find a different transaction's payload. The fix is to make the target explicit: stamp each paged payload with a monotonically increasing incarnation, copy it into the PageFetch at issue, and install/resolve only on a stamp match — which subsumes `orphaned_` as a special case.

2. **Page pins were leaked by every faulting read — fixed.** `ResolvePageWaiter` pins each fetched page for the waiting txn, and `ReleaseTxPagePins` had exactly ONE caller: `ReleaseCceLock`. That call is skipped whenever no lock was taken — the normal case for a ReadCommitted read under deferred acquisition — so every faulting read leaked its pins, `ShedColdPages` skipped the pinned pages, and nothing was ever evictable. `ObjectCcMap::Execute` now releases them at command completion (idempotent; §6 requires pins not outlive the command).

3. **Multi-command transactions spanning both payloads — fixed.** A tx can hold a fault context in BOTH objects: an early command faults on the committed object, a later one creates the dirty object and faults there. Once the dirty object exists every subsequent command of that tx runs on it, so it is authoritative. Two bugs followed from getting that backwards:
   - `BackFillPage` checked the committed payload first, so the older already-resolved context shadowed the live one — `ResolvePageWaiter` returned its now-null `parked_req_` and the waiting command never woke. Now routes **dirty first**.
   - `ReleaseTxPagePins` released only `cur_payload_`, stranding the dirty object's pins so those pages never became evictable. Now releases on both.

   Verified with MULTI transactions (read then write on the same paged key, under a 64 MB budget): 0 errors, correct values, server alive.

4. **Payload removal paths now run the §7 rules too.** `ApplyPayloadSwapRule` was called only where a dirty payload replaces the committed one. Two TTL-expiry retire paths (`object_cc_map.h`, the read/write early return and the no-buffered-commands branch) nulled `cur_payload_` outright, so a retired paged object took its `tx_contexts_` — and every request parked on one of its pages — down with it, and its in-flight fetches were never orphaned. Both now call the rule first. Verified: 50 paged hashes with a 6 s TTL, read after expiry under a 64 MB budget — all retire correctly, post-retire writes succeed, no corruption.

   **Verified by reading, not by test:** the swap-with-fetches-in-flight case itself. `FetchHub::Empty()` covers `orphans_` as well as `live_`, so `IsEmpty()` cannot recycle a lock structure with an outstanding orphan, and every outstanding fetch independently holds an entry pin. Entry pins stay balanced across a swap (fetches release theirs in `PageFetch::Execute`, which still runs when orphaned; parked readers release theirs via the `BlockOnPageFault` resume after `AbandonAllTxContexts` re-enqueues them), and other readers' per-page pins correctly need no unwinding since those counts die with the superseded object. Nothing in the gate or the soak forces a swap while fetches are in flight, so this path has never actually executed under test — it deserves a targeted one.

4. **Page copy-on-write implemented (§7).** The copy constructor now SHARES page buffers instead of deep-copying them, and a new `MutableView()` copies a page the first time it is written when `use_count() > 1`; `Put`, `Del` and `SplitPage` route through it, while reads keep the const `View()`. `InstallPage` likewise allocates a fresh buffer rather than overwriting a shared one. This removes a per-write duplication of the entire resident page set (~200 KB for a 900-field hash at 4 KB pages, since a write transaction clones the committed object) and — more importantly — it is what finally makes §9's zero-copy flush claim TRUE: the export shares buffers, so a write concurrent with a flush now copies instead of mutating bytes the flush worker is about to write out. Before this, that comment described an intent the code did not implement.

   Covered by three new tests in `paged_eviction_test.cpp`, each confirmed by fault injection (reverting `Put` to the non-COW view fails the clone/source divergence check): buffers shared on clone and split on first write with the source unchanged; an exported flush page byte-identical after a concurrent write to it; and shedding a page a clone still shares neither disturbing the clone nor actually reclaiming memory (§8's accounting caveat).

   Shared install is now done: `BackFillPage` builds the fetched bytes once and hands the same `shared_ptr` to every target via `InstallPageShared`, instead of allocating and copying per payload.

5. **Swap/retire with a page fetch in flight — NOW COVERED, and it found a bug.**

   Three Debug-only pieces were needed: `stall_page_fetch` (holds a fetch completion in the shard queue ~3 s), `shed_all_pages` (strips every evictable page and KEEPS the entry, giving the "metadata resident, pages shed" state a read must hit to page-fault), and `force_shard_clean_now` — which dispatches `CcShard::Clean()` onto every shard through `CcShard::DispatchTask`/`RunOnTxProcessorCc`, bypassing the two gates that otherwise make eviction unreachable in a test: `ShardCleanCc` is only enqueued by `WakeUpShardCleanCc()` when the memory wait list is non-empty, and its `Execute()` then requires `shard_heap->Full()` AND `NeedCleanShard()`. An earlier `--force_shard_clean` flag patched only the inner gate, could never work, and has been removed.

   One further precondition cost several failed runs: freshly written pages are DIRTY and are never shed, so the test must wait for a checkpoint before arming `shed_all_pages`, or the target object is skipped and the read never faults.

   `tests/unit_cc/swap_with_inflight_fetch.py` now genuinely reaches the path — verified by instrumenting `ApplyPayloadSwapRule`, which orphaned live fetches where every earlier version of the test orphaned zero.

   **Result: overwrite passes, delete and expire HANG.** With `SET` over the key the parked reader wakes, re-runs against the successor payload and correctly returns `-WRONGTYPE`. With `DEL` or `PEXPIRE` the reader never wakes (socket timeout) while the server stays responsive and uncorrupted.

   **Root-caused, by measurement.** Logging the actual fetch result settled it, and corrected two wrong inferences of mine along the way — the fetch does NOT error, and the resumed command is NOT executing on a deleted object:

   ```
   DBGF key=swap:delete page=52 err=0 status=0 bytes=4096 orphan=0 payload_status=2
   ```

   The fetch succeeds with a full 4 KB page. What has changed is `payload_status` — after `DEL` the committed paged payload is DROPPED (`cur_payload_ == nullptr`), and with it the `tx_contexts_` holding the parked request pointer. `BackFillPage` then has no object to resolve waiters against, so the parked reader is never woken and its client waits forever.

   Two fixes landed, both correct and both insufficient on their own:
   - `ConsumeTxFetchError` (interface + object + `BlockOnPageFault` resume): a woken command now fails with `DATA_STORE_ERR` instead of silently re-running when its fetch failed — §4 required this and it was missing.
   - `BackFillPage` no longer conflates two questions. Waiter ownership is now "whichever paged object holds their contexts, whatever the record status", while INSTALLING bytes still requires `PayloadStatus() == Normal`. Previously one status check gated both, so a fetch completing after a deletion resolved no waiter at all.

   Neither helps when the payload is dropped outright, because both the parked-request pointer and the error flag live INSIDE it.

   **Fixed: per-txn wake state now lives on the entry.** `FetchHub` owns a `TxWake` record per tx number (`parked_req_` + `errored_`), with `RegisterWaiter` / `ResolveWaiter` / `ConsumeError` / `ForgetWaiter` / `TakeAllParked`. The payload keeps only PAGE-scoped state: `NotePageFetched` pins the fetched page for the txn, `EnsureTxFaultContext` creates the context that holds those pins, and `HasPageWaiter` still answers the per-waiter routing question. Three call sites moved: the park registers on the hub, `BackFillPage` wakes from the hub unconditionally (a null payload no longer skips the wake), and the `BlockOnPageFault` resume consumes the error from the hub.

   Two follow-on gaps surfaced immediately and are also fixed: `ApplyPayloadSwapRule` now takes parked requests from the hub rather than the payload (which had just been emptied of them), and an ORPHANED fetch — which skips `BackFillPage` entirely — now releases its waiters before returning, so a superseded payload cannot strand them.

   `swap_with_inflight_fetch.py`: overwrite `-WRONGTYPE`, delete `$-1`, expire `$-1` — **all three PASS**. Regression clean: three paged unit suites exit 0, hash TCL suite 0 errors / 0 exceptions, and eviction under a 64 MB budget still serves 40 paged objects with 0 wrong reads.

3. **Eviction verified working under real pressure.** With all four fixes in, a 64 MB / 2-core node under a ~50 MB working set sheds in the designed 10 % batches (`resident=74 shed=7`, `67/6`, `50/5`, `45/4`), reclaims memory (ends at `heap full: 0`, 22 MB allocated), and completes a 120-key × 900-field write phase without hanging. Regression gate green afterwards: hash TCL suite 0 errors, all three paged unit suites exit 0.

   **Still open:** at maximum client write rate (`soak.py` with no pacing) the same node can still saturate — memory fills faster than checkpoint plus eviction reclaims and requests park. With modest pacing between pipelined batches it keeps up. This looks like a backpressure/throughput limit at an extreme budget rather than a deadlock, but it has not been characterized, and Phase 5 should not be closed until it is.
**The fault-path throttle is DEFERRED, not outstanding.** §8 proposed parking a faulting command on the shard's memory wait list before issuing its fault set, so read-driven page-buffer growth cannot overshoot the budget. Decision (2026-07): this is properly a page-ALLOCATOR concern, and the natural time to address it is alongside zero-copy I/O, where page buffer ownership is being reworked anyway. Not a gap in Phase 5.

   For the record, if it is ever revisited: it needs a distinct "blocked on memory" block type that the resume path understands (alongside `BlockOnFetch`/`BlockOnPageFault`). A naive version that reused the existing wait list corrupted a mid-flight request, because parking requires clearing per-attempt state the request is still using. Note also that nothing currently applies backpressure to page allocation at all — page buffers come from plain `new[]`, which never consults the shard budget and never fails, so the engine's "allocation failed -> wait list" path does not cover them.

6. **Abort with a parked command — COVERED.** `abort_parked_waiters` (Debug only) aborts whatever is parked on a fetch WITHOUT deregistering it, which is what a real abort path does: a deadlock victim, tx recovery or a term change knows nothing about page fetches. `tests/unit_cc/abort_with_parked_command.py` drives it for a parked read and a parked write, and verifies by log that the abort actually fired (an earlier version passed while aborting nothing, because the injector sat AFTER BackFillPage had already woken the waiter).

   Both clients get an error reply, the server survives the completion that follows, and the key stays usable. One real gap was closed as part of this. `TemplatedCcRequest<ApplyCc, ...>::AbortCcRequest` Free()s the request back to its `CcRequestPool` while the entry's hub still holds it as a parked waiter, so a later completion would resolve a stale pointer and enqueue a recycled request. The fix belongs in `ApplyCc::AbortCcRequest`, which now clears the parking residuals before delegating to the base: it calls `CcMap::ClearPageFaultParking` (no-op by default, implemented by `ObjectCcMap`), which forgets the wake record, releases the txn's page pins, releases the entry pin the park took, and recycles the key lock.

   An earlier attempt put this in `ReleaseTxPagePins` instead. That was wrong: it runs from `ReleaseCceLock`, which a lock-free ReadCommitted reader never reaches, so an aborted parked READ kept its stale registration. Only the request itself knows it was parked, so only the request's abort can undo it.

7. **Fault matrix over the three dimensions that page-fault handling has — `tests/unit_cc/paged_fault_matrix.py`.** Ten scenarios across: fetch outcome (delayed | errored), transaction shape (single command | contexts in BOTH the committed and dirty object), and concurrent change (none | deleted | overwritten by a non-paged value | overwritten by a NEW PAGED incarnation | tx aborted). Every scenario asserts its own preconditions — that pages were shed, the stall fired, the error was injected, the abort fired — and its expected REPLY, so a scenario cannot pass while exercising nothing. Injectors: `stall_page_fetch`, `fail_page_fetch`, `shed_all_pages`, `abort_parked_waiters`, `force_shard_clean_now`, all Debug-only.

   It found two product bugs on its first honest run:
   - **An errored page fetch hung the command forever.** The `BlockOnPageFault` resume read the error flag AFTER `ReleasePin()`/`RecycleKeyLock()`, and when that was the last pin the lock structure holding the hub was destroyed, making the flag unreadable. The command re-ran, faulted on the same page, parked, errored — a loop. The error is now consumed before the structure can be recycled. This path had never executed before.
   - **A read of a DELETED key reported a storage error instead of nil.** `ResolveWaiter` was being passed the INSTALL result as its success flag; the two differ exactly when the payload vanished (nothing to install into, but the store succeeded). It now takes `fetch.error_code_ == 0`, and the install result governs only pinning.

   Two bugs in the test instrumentation itself are worth recording, since both produce meaningless greens: `LOG_FIRST_N` stops logging permanently once its budget is spent, so every scenario after the first saw a zero delta; and `force_shard_clean_now` capped its sweep at 64 rounds, which never reaches a freshly written object because the LRU sweep starts at the cold end.

## Phase 6 — Replay, standby, migration (data_substrate)

`CommitOn`-may-fault through the buffered drain; `kDrainTxn` registration + count-at-zero re-drive + per-head-command pin release; standby fast-path divert-to-buffer on not-ready; the sharpened reopen trigger (`front().obj_version_ > CommitTs()`, EloqStore-gated code); `UploadBatchCc` metadata+dirty-pages envelope with dirty install at the target; `UploadTxCommandsCc` needs no change — test it anyway (§10).

**Landed so far (6a, partial):** the paged `Commit*` methods are discover-then-mutate — they record every missing page in one pass and return `false` without touching the object, so a faulting commit is retryable rather than half-applied. The engine reads that signal through `PagedCommitApplied()` in `object_cc_map.h`, which distinguishes "same object back because it mutated in place" from "same object back because it faulted" by asking `PagedTxObject::HasPendingFaults()`. `CommitCommandOnPayload` / `CommitCommandOnDirtyPayload` now return whether the command applied.

On the four `ApplyCc` call sites a fault is impossible — `ExecuteOn` ran earlier in the same transaction and pinned every page it touched, and the shed policy skips pinned pages — so they assert rather than handle it. That assert is the point: without it, the new `false` return would silently drop the write.

**Landed (6a, drain re-drive):** the drain reports page-fault stalls instead of silently skipping. `TryCommitBufferedCommands` returns whether it ran to completion; on a paged fault it stops at the faulting command, records `TxnCmd::applied_prefix_` so the commands of that transaction that already ran are not applied twice, and leaves `cur_ver` where it was. The `ObjectCcMap` callers then call `IssueDrainFetches`, which fetches the missing pages under the reserved `kDrainTxnNumber` — pins and all, so the eviction pass cannot shed them back out — and `BackFillPage` calls `RedriveBufferedDrain` when that context's outstanding count reaches zero. `ResolveWaiter` gained a `reached_zero` out-param, because the drain's parked request is legitimately null and "nullptr" alone cannot distinguish "run the drain" from "still waiting".

**Replay abort found and FIXED by the replay test.** A crash-restart of a paged hash aborted on restart at `object_cc_map.h`'s "The data log all processed, but there are still some commands in buffered cmd list" — an `assert(false)`, so a Debug node never came back up. Three distinct defects, all fixed:

1. **The end-of-replay leftover-buffer check did not allow for a pending page fetch.** This was the actual abort. A paged drain stops on a non-resident page, issues the fetch, and leaves its commands buffered — a normal transient state. But log replay finishes in far less time than a page read from the store takes, so the check saw buffered commands, declared the missing-version inconsistency, and asserted. `DrainFetchPending()` now guards that branch: while the entry's hub still owns any fetch (live or orphaned by a §7 payload swap — both still complete and still resolve the drain), the commands are left alone for the completion to re-drive.
2. **Drain fetches were stamped with the wrong term.** During replay the node group's leader is only a *candidate*: the real term is still -1 and the node is not yet serving, becoming real only when replay finishes. `IssueDrainFetches` used the bare `LeaderTerm()`, recording -1, while `FetchRecordCc::ValidTermCheck` at completion compares against `max(CandidateLeaderTerm, LeaderTerm, StandbyNodeTerm)` — so no completion could ever validate. `DrainFetchTerm()` now mirrors that maximum, at both issue sites and the re-drive's `ng_term > 0` guard, which had the same defect.
3. **`PageFetch::Execute` abandoned every waiter when `ValidTermCheck()` failed on a non-orphaned fetch.** `BackFillPage` was skipped, and the orphan branch below does not run for a fetch that was never superseded, so nothing resolved the waiters — a permanent hang for a parked command and a permanently stuck buffered list for the drain. Waiters are now resolved with an error in that case.

After these, the restarted node comes up (banner present), page fetches complete, and the assert is gone.

**Retracted: there is no post-checkpoint write-loss bug.** An earlier version of this note reported that only the first of 300 acknowledged writes to one key survived a restart, in both paged and non-paged configurations. That was a defect in `tests/unit_cc/replay_paged_restart.py`, not in the engine. The batched pre-checkpoint phase drained its replies with a single `recv()`, which is not guaranteed to consume all 150 of them; the leftover bytes then satisfied the post-checkpoint phase's raw byte count (`4 x 300`) early, so the SIGKILL landed before most of those writes had committed and the restart legitimately replayed one command. The control configuration "confirming" the loss was the same harness bug, not corroboration.

Two measurements settled it. Instrumenting the replay emplace path showed exactly ONE command arriving for the key, so the loss was upstream of the buffered-command machinery entirely. A strictly synchronous probe -- 20 `HSET`s, each reply read before the next send, then SIGKILL -- recovered all 20 after restart with 20 commands replayed, proving WAL durability and replay are correct for acknowledged writes.

The harness now writes the post-checkpoint tail one command per round trip on a fresh connection, asserting each reply, and the batched phase drains its replies fully. With that fix the full-scale test passes: 900 + 300 writes, `content_ok=True drain_stalled=True`, every field recovered and the drain provably stalling on a non-resident page. The same test with conversion disabled reports `FAIL(vacuous: replay never page-faulted)`, which is the precondition assertion refusing to claim a pass for a configuration that cannot exercise the path.

**The deferred-promotion gate is load-bearing, and it is what makes the safety property hold.** `tests/unit_cc/replay_serving_window.py` establishes the chain:

- The listening port accepts connections only AFTER promotion. Proven by the wedged run: with a 3000-command tail the drain could not finish inside the deadline, the gate refused to promote, and the node never printed its "Server Started" banner nor accepted a connection for 90 s.
- Without the gate, promotion happens as soon as `on_fly_cnt` reaches zero, and post-barrier measurements show real work still outstanding at that moment (`drain=1 buffered=1 fetches=0`, or `buffered=1 fetches=1`). The port would then open over a partially applied object.
- With the gate, every observed run answers its first client command with the COMPLETE object (`:1200`, `:1700`), and the deferral is confirmed in the log each time.

The test reports `INCONCLUSIVE` rather than `PASS`, deliberately: it was written to catch a client command being rejected inside the window, and the gate works by ensuring no such window exists. There is nothing to sample. That is recorded as INCONCLUSIVE rather than green so the distinction is not lost.

**Open issue: the 60 s promotion deadline does not scale with the WAL tail.** With 3000 buffered commands, 238 units of replay work were still outstanding at the deadline, so the node refused to serve and stayed down. The drain applies buffered commands one at a time and faults per page, so recovery time grows with the tail rather than being bounded. A fixed absolute deadline is the wrong shape: it should be progress-based (reset while the outstanding count is falling, fail only when progress stalls), so a large but healthy tail is not mistaken for a stuck drain. Also note the deadline log summed three different quantities and called them "paged object(s)"; it now names them and says so when the key list is legitimately empty.

**RESOLVED: a replay stall that blocks promotion is fatal — the node logs and shuts down.** First observed on a restart whose store had just been through the whole fault-injection battery (`fail_page_fetch`, and `stall_page_fetch` armed with count -1 and fired 1.4 million times). After replay the node reported `47 buffered command(s), 0 parked drain(s), 0 in-flight record fetch(es)` — buffered work with nothing outstanding that could ever drain it. The progress-based detector fired correctly every ~30 s ("NO progress for 30984 ms, best seen 47"), and then `AwaitDrainsAndPromote` simply returned, by the rule then written into it: never promote with work outstanding. The node stayed a CANDIDATE and never opened its port; twelve minutes later it was still logging the same ERROR from a fresh waiter thread each round, because the replay-done path kept starting a new waiter that re-detected the same stall.

The decision: replayed commands that can never be applied mean acknowledged writes cannot be reconstructed from the log plus the store — that is data corruption, and neither survivable answer is acceptable (promoting serves an object missing acknowledged writes; staying a candidate is a zombie with no operator escape hatch). `AwaitDrainsAndPromote` now emits a `LOG(FATAL)` naming the outstanding counts and any parked-drain keys, and the process aborts. A crashed process is visible to an operator and to supervision; a permanently unpromotable node is not. The FATAL also removes the waiter-churn/log-spam problem, since there is no process left to re-arm.

Not reproduced on a clean restart. `replay_paged_restart.py` against a server that had not been fault-injected passes with `content_ok=True drain_stalled=True` — the drain genuinely stalls on a page and recovers, and the count moving resets the stall clock, so a large-but-healthy tail does not trip the FATAL. The trigger here was state the injectors left behind, not an ordinary crash.

**FIXED: the replay path detected a paged page fault and then dropped it, so no fetch was ever issued.** This was a defect in this work's own Phase 6a wiring, not in the log service, truncation, braft, or the paged checkpoint -- all of which were measured sound while chasing it.

`IssueDrainFetches` was wired into `BackFill` and `RedriveBufferedDrain`, but log replay drains through `CcEntry::EmplaceAndCommitBufferedTxnCommand`, which **discarded** the drain's `false` return with a comment asserting that "the ObjectCcMap callers" would issue the re-drive. On the replay path they do not: `BackFill` runs only on a record fetch, and that does not recur once the record is loaded. So the object recorded pending faults, nothing issued the page read, and the drain re-ran forever.

Evidence, all from ONE run (mixing runs is what made this take so long -- see the reproducer notes):

```
FIRST drain_call  deque=63   head_obj_ver 0.62 s ABOVE cur_ver   paged=1  pending_faults=0
LAST  drain_call  deque=363  head_obj_ver == cur_ver (chains)    paged=1  pending_faults=1
drain_page_stall=0   drain_completion=0   drain_redrive=0   drain_call=6472
```

The last line is the whole bug: the head chains, the object is paged, `CommitOn` runs and records a fault -- and zero fetches are issued across 6472 drain invocations while the buffered list grows.

The fix makes `EmplaceAndCommitBufferedTxnCommand` return whether the drain finished, and the two `ReplayLogCc` call sites in `ObjectCcMap` call `IssueDrainFetches(cce, DrainFetchTerm())` when it did not. `CcEntry` cannot issue the fetch itself -- it has no route to the store -- so the signal has to leave the class.

Result: 4 of 4 runs clean where ~6 of 10 previously stalled, with the full chain active (fetch issued -> completion -> re-drive). Fetch counts exceed re-drive counts because one stall can await several pages and the re-drive fires once at zero.

**Verified sound while eliminating suspects** (keep these; each cost a cycle to establish): truncation (log watermark below the store version, replay starts at watermark+1); braft durability (own fsynced log, replays into the state machine, so `disableWAL` on the log-state RocksDB is safe); apply-lag (whole window applied before `ReplayLog`, which is leader-gated anyway); the node-group filter in `WriteToStreamInBatch` (`filtered_cnt=0`); shipping range (`min_shipped < cur_ver < head < max_shipped`); record delivery (every command arrives, duplicates correctly deduped by `EmplaceTxnCmd`); and the paged checkpoint (export writes the entry's own `commit_ts`, metadata lands under the object key at that version, recovery reads back exactly that version).

**Checked and closed: `HLEN` does not under-report on a paged object.** `tests/unit_cc/paged_hlen_consistency.py` writes 1200 fields one round trip at a time -- each reply read before the next send -- and compares `HLEN` against an independent `HKEYS` array length and against the number of distinct fields written, on every write near the start and through the whole tail. Result: 1200 / 1200 / 1200, zero mismatches. The read path is correct.

What prompted the check was an object holding one MORE field after recovery than a pre-crash `HLEN` reported (1700 -> 1701, and 3900 -> 3901, every write acknowledged). That was seen only while the replay drain was dropping its page-fault signal, with commands sitting unapplied and being re-shipped repeatedly. Since that fix, four consecutive window runs measure 1700 before the kill and 1700 after. Recorded as a symptom of the fixed bug rather than as fixed in its own right, because the exact path was never traced -- if it reappears, it is a real defect and not a test artifact.

Reproducer notes: judge the restart by the "EloqKV Server Started" banner or by the assert, never by the listening port — brpc opens the port before replay finishes, so a port poll succeeds while the process is already aborting. The `FAULTLOG drain_*` markers are `DLOG(INFO)`, which glog does not flush on `abort()`; raise the ones you need to `LOG(ERROR)` first. An earlier pass through this bug misattributed it twice — once to a version hole, once to a recycled lock structure — because a zero count on an unflushed `DLOG` was read as evidence.

**Not yet verified end to end.** This path is only reachable from replay, standby or migration, and `tests/unit_cc/replay_paged_restart.py` (written for it, with a `FAULTLOG drain_page_stall` precondition) cannot run yet: a local single-node server with `enable_wal = on` came back from SIGKILL with no replay line in its log and had lost every acknowledged post-checkpoint write. A control run with conversion disabled lost the same writes, so the gap is the harness's log-service setup, not this code. Standing that up is the Phase 6 harness item, and it gates the exit criteria below.

**Still open in 6a/6b:** nothing yet reacts to a fault on the two paths that genuinely have no pins, because per #509 they run `Deserialize` + `CommitOn` with no `ExecuteOn` — the standby fast-path apply (marked `GAP` in `object_cc_map.h`) and WAL replay. Diverting those to the buffered-command branch has to be decided *before* the batch's first command is applied, since a command that already ran cannot be taken back; that ordering constraint, plus `kDrainTxn` and the count-at-zero re-drive, is the remainder of the work.

**Tests:** kill-mid-trace recovery ⇒ layout-identical replay (§16); reopen-suppression regression (page-blocked head must not spin the store); standby apply under forced faults + promotion ⇒ first checkpoint writes a coherent object; migration with updates in flight ⇒ target serves reads, faults clean pages, flushes shipped dirty pages; conversion mid-replay and threshold-skew divergence self-heal (§11).

**Exit criteria:** failover/migration test matrix green; a promoted divergent-layout standby leaves only sweeper-class orphans (verified by store scan), never corruption.

### Phase 6b — standby (landed; bucket migration deferred past v1)

**A paged payload never takes the standby's direct-apply fast path.** Per #509 a standby-forwarded command reaches `CommitOn` without ever running `ExecuteOn`, so no page is pinned and `CommitOn` can fault partway through a batch -- and a command that has already run cannot be taken back. The decision therefore has to be made BEFORE the first command of the batch is applied, which rules out reacting to a fault once one occurs. `Execute(KeyObjectStandbyForwardCc)` now diverts any paged payload to the buffered-command branch, which handles the fault properly: the drain stops on the missing page, the caller issues the fetches, and the completion re-drives.

This is deliberately conservative -- it diverts whether or not the particular batch would have faulted, because that is not knowable without running the commands. The cost is the fast path for large objects on a standby; the alternative is a half-applied batch with no way to undo it.

The standby's buffered branch also now calls `IssueDrainFetches` when the drain stalls. Without it the fault is detected and then dropped -- exactly the defect that stalled log replay until the `ReplayLogCc` sites were given the same call.

**Reopen trigger sharpened.** `FetchRecordCc` reopened whenever the buffered list was non-empty. With paged objects a buffered head can be waiting on a PAGE rather than a missing version, and re-fetching the record then changes nothing: same version back, head still cannot apply, reopen again -- spinning against the store while racing the page fetch already outstanding on that entry. It now reopens only when the head wants a version newer than the one the fetch just delivered (`front().obj_version_ > rec_ts_`). Compared against `rec_ts_` rather than the entry's commit ts because `cce_` is an `LruEntry` there and the commit ts lives on the versioned subclass; it is also the more direct question, "is what I just fetched too old for the head?".

The predicate is computed OUTSIDE the `DATA_STORE_TYPE_ELOQDSS_ELOQSTORE` guard so it compiles and is syntax-checked in every configuration -- only the reopen itself is EloqStore-specific. The first version of this change sat entirely inside the guard, did not compile in the RocksDB dev build, and shipped a reference to a member that does not exist on `LruEntry`.

**Verified end to end on a two-node EloqStore cluster.** `tests/unit_cc/standby_paged_apply.py` (apply) and `tests/unit_cc/standby_failover_paged.py` (promotion) run a real leader/replica pair against MinIO. Both pass with WAL off and with WAL on, and the apply test refuses to report PASS unless the restarted replica's own log shows `FAULTLOG drain_page_stall` — measured 46 faults (WAL off) and 87 (WAL on), against a final object identical to the leader's. Failover: `FAILOVER TO` promotes the replica, it serves the complete object, takes 300 further paged writes, and all 700 fields come back coherent after both nodes are killed and restarted.

**Reaching the divert needs a FETCHED object, not a shed one.** Two routes produce a paged object on a standby and only one can fault:

- *built* — the standby applied every command itself. Conversion happens inside `CommitOn` (`HSetCommand::CommitOn`), precisely so standby and replay converge on the same representation, so the standby really does hold a paged object — but it created every page, so all of them are resident and nothing can fault.
- *fetched* — the standby restarted and a forwarded command found no entry, so `FetchRecord` read the record back. A stored paged object is metadata only, its pages living under separate keys, so it arrives with ZERO resident pages and the next `CommitOn` faults.

`shed_all_pages` cannot substitute for the second. It sheds only pages whose `flushed_` is set, `flushed_` is set by the checkpointer, and a standby never checkpoints — `EvictablePageCount()` on a standby is therefore always zero. Two rounds of testing "passed" on that route while the standby never faulted once. The test now keeps writing on the leader *after* the replica is back, which is what puts commands on a freshly fetched object.

Worth noting for §8: a standby cannot shed pages at all, so it gets none of the partial-eviction benefit. Whole-entry eviction still applies. Not a v1 blocker, but it means standby memory for paged objects is bounded only by the entry-level policy.

**Deployment facts the harness pinned down** (none paged-specific, all of them cost time to rediscover):

- **Roles are not pinned by config.** Both nodes are in one node group and the leader falls out of the election, so a run can come up with either port serving writes. The tests discover roles rather than assume them.
- **Crash failover does not work at this replica count, by design.** `node_group_replica_num = 1` gives the group no second voter, and each node runs its own host manager, so killing the leader leaves the host-manager raft group without quorum: the survivor logs `WRITE_REQUEST_ON_SLAVE_NODE` indefinitely and is never promoted. Automatic failover needs 3. The graceful `FAILOVER TO <host:port>` exercises the same engine-side promotion and is what the test uses.
- **The log service must be external for any failover test.** With the built-in log service, log group 0 lives *inside* the leader process (`local_port + 2`), so killing the leader takes the WAL down with it and the replica hangs trying to reach it. The harness runs `launch_sv` standalone (1 replica) and points both nodes at it with `txlog_service_list`. `launch_sv` is only built by the log service's own CMakeLists (`TEST_LOG_SERVICE`), not by the EloqKV build.
- **Bootstrap needs a clean cloud path.** Wiping the local data directory while leaving objects under the EloqStore cloud prefix makes startup fail with `EloqStore start failed with error code: 16`, surfacing as `READ_CATALOG_FAIL`. Each clean run needs a fresh `eloq_store_cloud_store_path`.
- **A membership change briefly costs the leader its ability to start transactions** (`Failed to initialize the transaction` for a few seconds after a node joins or leaves). The tests wait it out; it is not a paged-objects effect.

**Reaching the fault deterministically needs the replica primed with a read.** Left to chance the outcome alternates between 87 faults and 0: if the leader has already checkpointed past the arriving commands the replica discards them (`commit_ts < NativeNodeGroupCkptTs()`), never builds the entry, and serves later reads from the store — a correct path that faults nothing on the apply side. `standby_paged_apply.py` therefore issues an `HLEN` on the restarted replica before the final write burst. `HLEN` answers from the metadata block alone, so serving it pulls the record back and leaves the object exactly as a fetch delivers it — metadata resident, every page non-resident — and the next `CommitOn` then faults by construction. Two consecutive runs after this change: 87 faults each. The `HLEN` must be retried until it answers; a replica that has just opened its port can still refuse reads, and an errored read primes nothing.

**Reopen trigger verified, on a sample of one.** Measured by temporarily logging both predicates at `FetchRecordCc`'s decision point during a standby run: 87 page stalls, one `FetchRecordCc` completion, and that completion had `buffered=1, version_hole=0` — the head was blocked on a page, not on a missing version. The old predicate would have reopened there; the sharpened one did not. Because a reopen returns the same version and leaves the buffer non-empty, the old predicate would then have been true again on the next completion, so what was suppressed is a spin, not a single redundant fetch. One occurrence is thin evidence of frequency but sufficient evidence of reachability and of correct handling.

**`DrainFetchPending` is live, and must stay a branch rather than an assertion.** It guards `ObjectCcMap::BackFill`'s leftover-buffer handling, which is the same fetch-completion path the standby runs drive (the 87 stalls are issued from `if (!drained) IssueDrainFetches(...)` a few lines above it). Buffered commands plus an outstanding page fetch is a normal transient state there; the branch below it clears the buffer and asserts, which would abort a node that is merely mid-fetch. Note the clearing branch is additionally gated on `LeaderTerm(cc_ng_id_) > 0`, so on a standby — where the positive term is the standby term — neither branch is reachable; the guard earns its place on a restarting leader whose replay left commands buffered behind a page.

## Phase 7 — HSCAN, observability, tools (eloqkv; parallel-friendly)

HSCAN cursor (§12); `OBJECT ENCODING`/`MEMORY USAGE` (resident vs logical)/`DEBUG OBJECT` semantics + metrics (page/resident counts, fault rate, per-state park counters) (§15.3); `eloqkv2rdb`/`eloqkv2aof` reassembly of metadata + pages (§13).

**Key test:** the SCAN-guarantee property test — concurrent inserts/deletes/splits/directory doubling during a scan; assert every element present throughout is returned at least once (duplicates allowed, skips fatal).

**Exit criteria:** property test green; tools produce RDB/AOF that real Redis loads with identical content.

### HSCAN — landed, with a design correction

The cursor that shipped is **a plain ascending `hash32` bound** (`PagedHashCore::ScanStep`), not the reverse-binary directory walk this phase originally called for. The original prescription was measured wrong for this directory: reverse-binary solves *low-bit* bucket indexing (children `j`, `j+2^d`), while §4's directory routes by *top* bits (children `2j`, `2j+1`) — a reverse-binary walk resumed from a stale index after a depth-4 → 12 doubling covered only **3328 of 4096** directory entries. Page sharing masked the hole from the original scan-guarantee test (a skipped entry loses data only once its page stops being shared with a visited one); `TestScanDoublingMidScan` now forces post-doubling splits until entries are exclusive. §12 in the design doc records the full argument.

Two more §12 rules got real enforcement on the way: the equal-hash-run rule is now actually implemented in `ScanBucket` (it was only claimed in a comment; without it a cap landing inside a run of genuine 0-hash entries returned cursor 0 and skipped the run's tail), and `COUNT` now bounds **work** pre-`MATCH` rather than results (a non-matching pattern used to walk — and fault — the entire object in one call).

Verified: core property tests (`TestScanGuarantee` with mid-scan delete, `TestScanDoublingMidScan` with mid-scan doubling + 3000 splitting inserts) and the protocol-level `tests/unit_cc/paged_hscan.py` — full-loop completeness (2000/2000 fields in exactly `nfields/COUNT` steps), the MATCH work bound (200 steps, not one giant reply), and a scan under concurrent writes losing no pre-existing field. TCL hash suite clean against the same server.

### MEMORY USAGE — fixed

`RedisMemoryUsageCommand::ExecuteOn` returned `SerializedLength()`, which for a paged object is the METADATA ROW — a client's multi-hundred-KB hash reported a few hundred bytes (~10000× under). It now returns `LogicalBytes()` for paged objects (the §4 whole-object size the conversion threshold and MAX_OBJECT_SIZE already use; O(1) from metadata, and stable under eviction/fault-in, unlike a resident-bytes answer). Verified live: 500 × 205-byte fields → `MEMORY USAGE` = 102508; monolithic path unchanged.

### OBJECT ENCODING / DEBUG OBJECT — deferred, with reason

EloqKV has **no `OBJECT` command and no `DEBUG OBJECT` at all** (nothing in the command table), so there is no encoding surface to extend — "OBJECT ENCODING for paged objects" would mean introducing a new command family, which is not a paged-objects delta. Deferred until those commands exist; ditto the §15.3 per-object metrics (page/resident counts, fault rate, per-state park counters), which need the metrics plumbing decision first. `TYPE` correctly reports `hash` (the base-type rule, tested).

### eloqkv2rdb / eloqkv2aof — guarded; reassembly deferred

Both tools now (a) **skip page rows** (`txservice::HasPageKeyMagic` on the key — a page row is a raw page image, and parsing one as an object reads its first byte as a type tag), and (b) **refuse the export loudly** (`LOG(ERROR)` + abort) on a `PagedHash`/`TTLPagedHash` metadata row, instead of the previous `assert(false)` that in Release fell through to a null deref — or, with a case added naively, a `static_cast` to `RedisHashObject` exporting an EMPTY hash for an object that has data. A backup silently missing objects is the worst outcome, so the guard fails the whole export. Verified by full-TU syntax check under the dev tree's flag set minus the store-type define — an approximation, since the tools only build for `WITH_DATA_STORE=ROCKSDB` / `ELOQDSS_ROCKSDB_CLOUD_S3` and neither is a current dev tree; the next CI run of those variants is the real compile gate.

Full reassembly, when it is built, should be **two-pass**, not buffered: the `\x00EKVPAGE` prefix sorts every page row of every object before all object rows, so a single ordered pass would have to hold the entire paged dataset in tool memory before meeting the first metadata row. Pass 1 streams object rows (skipping the page prefix) and retains only paged METADATA blocks (~0.01% of object size); pass 2 re-scans just the page prefix, where each object's pages are contiguous, reassembling and emitting one object at a time — peak memory one object, and the RDB/AOF formats do not care about emission order. Note the tools do not build for `ELOQDSS_ELOQSTORE` (v1's shipping backend) at all, so an EloqStore scan path is a prerequisite before reassembly matters in production.

## Structural refactor — the two-layer decomposition (landed)

The §4 "Ownership: two layers" design is implemented; the code now matches the design doc's sketches exactly.

**Engine (`data_substrate/tx_service/include/`):**

- `page_frame_table.h` (new): the vocabulary types (`PageId`, `PageIdRange`, `FreeRanges`, `PendingDelete(s)`, `PageBuf`, `PageSlot`, `TxPageContext`, `kDrainTxnNumber`, the LE/varint helpers under `txservice::paged_detail`) and `PageFrameTable` — frames, BOTH pin views, pending faults, the whole runtime id lifecycle (free ranges, pending deletes, high-water, `AllocatePageId`/`FreePage`), LRU + shed policy, install, `StampWrites`, a fully generic `OnFlushApplied` (mark flushed + drain pending deletes), and the metadata row's page-manager-section codec (`SerializeMeta`/`DeserializeMeta`/`RebuildFreeRanges`).
- `paged_tx_object.h`: `PagedTxObject` now CONTAINS `PageFrameTable frames_` and implements every engine-facing virtual over it, once. Type hooks: `SerializeMetadataRow`, `PageKind`, `MetadataRowTtl`. There is no live-id hook — liveness derives from the id partition (live = allocated − free − pending), so `ExportPagedFlush`'s deletion fan-out is generic too. Explicit defaulted copy/move (the user-declared destructor would otherwise suppress moves, silently degrading them to frame copies).

**On-disk key encoding hardened (wet cement, pre-production).** Three flaws in the page-key scheme and its enforcement, fixed before any production rows exist:

- *Prefix-unsafe key encoding.* The page key embedded the object key with no length field, so `page("a",0)` was a byte-prefix of `page("a\x00…",0)` and objects' page rows interleaved — breaking both the contiguity claim and per-object prefix delete (one object's prefix delete could remove another's pages). Fixed by a fixed-width 4-byte length prefix (`[magic][key_len][key][kind][page_id]`), making the object component prefix-free. The metadata-adjacency assumption is dropped: metadata rows stay under the plain object key and need not be near page rows.
- *Key-length overflow.* A 2048-byte user key plus 13 bytes of page-key overhead exceeded EloqStore's 2048-byte store-key ceiling (Debug assert, undefined in Release). Fixed by reserving `kPageKeyOverhead` (now 17 bytes) below the store ceiling in the public `MAX_KEY_SIZE`; the 4-byte length field keeps the non-EloqStore 32 MB limit intact.
- *Enforcement bypass.* The reserved-prefix and length checks lived only in the single-key `ExecuteCommand` overload; every multi-key command (MSET/MGET/DEL/EXISTS, MULTI/EXEC, WATCH, ZScan) skipped them — `MSET <derived page key> <v>` could overwrite a live page row. Fixed by centralizing on `RedisServiceImpl::CheckKeyAdmissible`, called over every physical key on every path.

**Store inputs were under-validated — hardened.** Page installation checked only byte count and id liveness, and metadata parsing acted on unbounded values, so a corrupt or mismatched store row could produce out-of-bounds reads, an OOM, an assert, or a silently wrong object rather than a clean error. Now, in three layers: the generic frame table bounds the page size, the id high-water (`kMaxPageCount`) and the pending list; `PageView::ValidateImage` checks the page's own framing (layout version, slot array, offsets, record varints, ascending hashes); and the type's `ValidatePageImage` cross-checks the image against its metadata (entry count, local depth) plus **routing identity** — every entry must route to the installed id, which detects a valid page of another id served under this one without needing a page-identity field. Cross-section checks run once both halves of a row are in: live ids below the high-water (previously an `assert` guarding an out-of-bounds `vector<bool>` write) and entry counts summing to the field count. Two allocation hazards were bounded before use: `vector<bool>(next_page_id)` and `large_runs_.reserve(run_count)` (the latter threw `bad_alloc` rather than returning false).

**Open, HIGH: deletion never fans out to the page rows — the implementation contradicts §16.** `paged_store_rows_oracle.py` shows both routes (HDEL-to-empty and DEL) removing the metadata row while leaving every page row behind (19 and 15 rows respectively, after a 12 s wait at a 5 s checkpoint interval; S0 reproduced HDEL-to-empty, S1 both). *FIXED, matching what §16 already specified.* Both commit paths — committed payload and dirty payload — now RETAIN a paged block on deletion (status `Deleted`) instead of nulling or lazy-freeing it, so `ExportForCkpt` still finds it and emits `ExportPagedFlush(for_deletion=true)`; the fan-out code already existed and already handled the deletion case, it was simply unreachable. The dirty path matters as much as the committed one, since that block becomes the committed payload at the swap. **FIXED — deletion now runs the §7 swap rule; and the negative control taught us the window's real shape.** The in-place `DEL` commit in `CommitCommandOnPayload` now calls `ApplyPayloadSwapRule(cce)` before retaining the block: in-flight fetches spliced to orphans, parked readers woken at the DEL, every tx context (and so every pin) dropped — which also makes the buffer release TOTAL, removing the "skip pinned pages" wart (the pin check in `ReleaseBuffersForDeletion` is now a guard against a missed abandon, not an expected skip). `cce` is threaded into the helper (asserted to be handed the entry's current payload, since the swap rule acts on it); the dirty-path deletion instead calls `AbandonAllTxContexts()` on the dead block only — it is not yet the current payload, and the dirty→committed install sites already run the full swap rule.

*What the negative control showed — and the sharper truth a review question then extracted from it:* with the swap-rule call removed, the new `delete_with_inflight_fetch.py` (shed pages → `stall_page_fetch` → reader parks with a fetch in flight → DEL → immediate 90-field recreate with ids restarting at 0 → assert the successor exact and the old incarnation absent) still PASSES, because every successor-install site runs `ApplyPayloadSwapRule` at the INSTALL. Three states, three different truths: (1) ORIGINAL code nulled the payload at DEL, so the recreate's install-site swap rule saw null and orphaned NOTHING — the stale-install scenario was a genuine live bug, not a defended one; (2) retain-only (the negative-control configuration) is defended at install, which is what the control actually measured; (3) retain-only STILL leaks the post-flush window — the flush callback releases the retained block with a bare `cur_payload_ = nullptr` and no swap rule, so DEL → flush lands → recreate → old fetch returns re-creates state (1) exactly, and a fetch only has to outlive one checkpoint interval. Deletion-time orphaning is therefore not defense-in-depth but the only placement covering all three phases: it cleans the FetchHub at the moment the object logically dies, before any later state can matter. Consequence: any single object whose between-checkpoint dirty set exceeds 2.5 % of shard memory can wedge its key — at a 1 GB/2-core node that is a ~13 MB write burst to one hash. Fix direction is the review's admission controller, designed in 08-paged-objects.md §8 ("Memory admission") and refined in review to its final shape: admission IS allocation (page buffers move onto the budget-checked shard heap; no shadow counters), all-or-nothing acquisition with free-before-park on the existing memory wait list, never-fits is a deterministic error, and the write/apply path allocates inside `CommitOn` with a "blocked on memory" park at the discover-then-mutate boundary (an `Execute`-side reservation is unworkable: write sizes are unknowable there, and replay/standby have no `Execute` at all). Termination rests on an explicit axiom — after a full clean pass the budget holds the largest object's dirty set plus one command's working allocations — with a stalled node the accepted outcome when a deployment violates it. Under that axiom the key-wedge above is reclassified: a 16 MB dirty set on a 256 MB node satisfies the axiom and the failure is the engine's data-sync scan heap (2.5 % of budget) being unable to carry an object the budget itself holds — a `data_substrate` sizing fix, not write admission. The poisoned-entry cleanup (orphan recovery must also clear dead pending-command state) is likewise an engine follow-up independent of paging.

**Memory admission — PARTIALLY IMPLEMENTED (read path), designed for the rest.** Landed: the `PageAdmission` gate (a thread-local hook installed for exactly the window in which a thread acts as a shard, beside the existing heap override), `CcShardHeap::CanAllocate`, a fallible `AllocPage`, and `PageFrameTable::ReservePageBuffers` — so a client fault set CLAIMS its page buffers before any fetch is issued, all-or-nothing, with `InstallPage` consuming the claim. A refusal kicks the clean pass and re-enqueues the request to re-run from scratch (NOT the shard's memory wait list: that needs a request carrying no per-attempt state, and this one has some by then — the use-after-free already recorded above; re-enqueueing yields the core to the clean pass and is what the store-`Retry` path here already does safely). A fault set larger than the whole shard budget can never be admitted, so it is an `OUT_OF_MEMORY` error rather than an endless wait. Reply materialization is now charged as `logical_bytes + elements × 48` rather than logical bytes alone, and `HRANDFIELD` with a negative count is bounded by it — `HRANDFIELD k -100000000` on a 200-field hash returns a too-big error instead of building a hundred-million-element reply.

The write-side park is IMPLEMENTED at the top of `PostWriteCc`: while the shard heap is over budget, a paged commit kicks the clean pass and re-enqueues itself holding the write lock — before anything is mutated, so re-entry is idempotent; aborts never park. Chosen over the other candidates deliberately: mid-`ApplyCc` parks are not restart-safe (`ExecuteOn` has run and forward entries would duplicate to standbys on a re-run), and the DRAIN is left ungated by decision — parking recovery on a transient over-budget window risks the promotion-deadline FATAL, a dead node, which is strictly worse than an axiom-bounded overshoot while applying the replicated stream. `CommitOn`'s interior allocations (`CreateDirtyPage`, the COW copy) stay unchecked via `AllocPageUnchecked` — a first attempt that gated them segfaulted immediately (a null buffer written through by `CommitOn`), direct evidence the park boundary is the only place refusal is possible. Verified by `tests/unit_cc/paged_commit_memory_park.py` (Debug, via `force_paged_commit_park`): writers stall while armed and complete on disarm, lock-free reads of the same key serve the pre-image throughout, other keys are untouched, and nothing is dropped. The monolithic `HRANDFIELD` negative count remains unbounded, as it was before paging.

**The scan-heap wedge — ROOT-CAUSED AND FIXED (engine bug, not a sizing problem).** The earlier diagnosis in this section was wrong and is retracted: the paged flush unit is *small* on the scan heap (a metadata row plus `shared_ptr` page refs — page bytes are never copied), so "the indivisible unit exceeds the heap" was never the mechanism. Instrumenting both scan-heap decision points showed the real one: **4.2 MB of residual with a completely EMPTY staging vec**, and popping 72 record husks freed 32 bytes. The scan heap's contract, encoded by `ReleaseDataSyncScanHeapCc`, is that what it allocates is freed on the same shard thread so the stats reconcile. A paged export violates it: the hand-off MOVES the `PagedObjectFlush` out of the scan-vec record into the flush pipeline, and the flush worker destroys it on ITS thread — and a cross-thread free never reconciles into this heap's stats (mimalloc, no `mi_heap_collect` by design). So every paged export ratcheted `allocated` upward permanently until the threshold was crossed and *all* exports were refused: a wedged checkpoint, then a wedged key. A monolithic export is immune because `SetNonVersionedPayload` serializes into a string that is destroyed on the shard thread — which is why an 8 MB monolithic hash sailed through the same harness.

Fix — revised in review to the monolithic-style discipline: the hand-off **COPIES** the `PagedObjectFlush` into the flush pipeline's record (under the ckpt heap) instead of moving it, so the staging original stays in the scan vec and is freed on the shard thread by `ReleaseDataSyncScanHeapCc`, exactly like a monolithic record's serialized blob. The copy duplicates no page bytes — the page list holds `shared_ptr`s, so copying bumps refcounts; only the metadata-row string and the id vector are duplicated (tens of KB, versus the multi-MB blob copy the monolithic path already pays). `ExportForCkpt` needs no special-casing at all. An interim fix (allocate paged exports under the shard heap) worked but was asymmetric and relied on the shard heap's reconciliation dynamics; it also briefly shipped a measurement regression — `Full()` reads the CURRENT default heap, so skipping the heap switch compared the shard heap's level against the scan threshold and refused everything — caught in test and gone in the final shape. Result on the wedge repro: scan-heap refusals 43 → **0**, "still full after release" → **0**, orphan-lock recoveries → **0**.

**The residual stall — EXPLAINED: a pathological page size, not a general defect, and it invalidates the harness's write-side numbers.** With the scan-heap bug fixed, growth still collapsed at a few thousand fields (batches 4 s → 72 s, ~600 ms per write). Eliminated by measurement, one config change at a time: not the scan heap (refusals now zero), not the WAL (`enable_wal = off` reproduces), not lock contention or page-fault parking (probes at both park points fired ZERO times), not flush backpressure (a full-process freeze shows every data-sync and flush worker idle), not the new §8 commit park (it never fired), and not the checkpointer (disabling it reproduces).

The variable is **page size versus record size**, and the numbers are stark. The harness ran 4 KB pages with 3 KB values — **one record per page**. At that setting growth stalls at ~4000 fields with the shard heap at **98 MB for an 11.8 MB object, an 8x amplification** (`heap full: 1`). Re-run identically with the DEFAULT 128 KB page size (~42 records per page): **8000 fields, ~22 MB logical, 52 s, no stall, shard at 43 MB** — a normal ~2x.

The mechanism is inherent to extendible hashing: directory size grows as O(N^(1+1/b)) in the number of records N for bucket capacity b, so b≈1 makes it QUADRATIC. Separating ~4000 single-record pages needs a directory of millions of entries — tens of MB, dwarfing the 16 MB of page buffers and matching the observed 98 MB — and every doubling reallocates and copies the whole thing, which is the ~600 ms write. So this is not a paging defect and not a memory-admission gap; it is a configuration in which the layout cannot work.

The depth arithmetic, simulated to pin it: the directory is `2^global_depth` entries regardless of page count, and the depth must exceed the longest common hash prefix over ALL PAIRS of keys — a birthday quantity, ≈ 2·log2(N) bits at capacity ~1, with huge variance because one unlucky pair sets the whole depth. At 4000-5500 random 32-bit hashes that is depth 22-28 → 4M-268M directory entries (17 MB-1 GB), which is why the stall point wandered between runs and why the shard held ~98 MB for a ~12 MB object (pages ~16-22 MB + a tens-of-MB directory + doubling copies). At the 128 KB default (capacity ~42), splits stop when ~42 keys separate and the directory stays KB-sized.

Two consequences. First, **every earlier "wedge at ~16 MB" observation in this document is this artifact**, including the one originally reported as a general write-side hazard — that framing is retracted; at the default page size the same workload runs clean. Second, a design refinement surfaced by review: §4's out-of-line large-value runs are the mechanism that keeps inline bucket capacity high, but "goes out-of-line" must be defined as **a fraction of the page size** — `record > page_size / k` for a small constant k — NOT "does not fit a page". Under fits-a-page semantics a 3 KB record in a 4 KB page is "normal", stays inline, and the capacity-1 quadratic regime remains reachable even after large runs land. Bounding inline records at page/k structurally bounds the directory at Θ(N^(1+1/k)) (Flajolet's extendible-hashing analysis) — essentially linear for k ≥ 8. This is the general answer to "is the data structure fragile?": extendible hashing is quadratic ONLY at capacity ≈ 1 and benign at practical capacities, and the out-of-line threshold is what guarantees the structure never operates near capacity 1. Recorded as a §4 amendment for the large-run implementation; until it lands, the practical note is that `--paged_hash_page_size` should not be set within a small multiple of expected record sizes (the 128 KB default is fine).

Verified: `TestMemoryAdmission` (all-or-nothing, nothing retained on refusal, never-fits vs merely-busy, claim consumed by install, write path exempt under a zero budget, scope restoration); the full paged battery, the fault matrix and the TCL hash suite pass with admission enabled; `HRANDFIELD -1e8` errors while `-50` and `HGETALL` are unaffected.

**Conversion was tied to one command — now an object policy.** §11's rule is about the object ("a hash converts when its post-image crosses the threshold"), but only `HSetCommand::CommitOn` applied it. Reproduced with `threshold=1`, using `DUMP` as the representation probe (it succeeds monolithic and refuses paged): `HINCRBY`- and `HSETNX`-grown hashes stayed monolithic while an `HSET`-grown one converted, so two hashes of identical content had different representations depending on how they were built, and anything grown only by the uncovered mutators could never page at all.

Centralized as `MaybeConvertHashToPaged` (`include/redis_paged_hash_object.h`), called on the post-image by `HSET`, `HSETNX`, `HINCRBY`, `HINCRBYFLOAT` and both `RESTORE` outcomes. It is total and self-guarding — null, already-paged, and non-hash inputs (RESTORE passes every type) return unchanged — so no call site needs a type test, and the three things a per-command copy would drop live in one place: the `AllRecordsFit` eligibility gate above, the page size read from config exactly once, and the TTL.

*Ownership at the import call site differs from the mutator ones, and the policy has two forms because of it.* A mutator's `CommitOn` is handed the **engine-owned** payload, and the engine destroys what it replaces when a different pointer comes back — so those sites pass a raw pointer. `RestoreCommand::CommitOn` instead **builds its object locally** and hands ownership out through its return value; releasing that object into the raw-pointer form and returning the paged twin would leave the source with no owner at all. Both import sites therefore pass the `unique_ptr` overload, which keeps the source owned until the verdict is known and destroys it exactly when it is replaced. This is a code-inspection finding, not a measured one: an RSS probe over `RESTORE ... REPLACE` could not isolate it, because the same ~290 KB/round growth appears with conversion **dark**, where this path cannot convert at all. That baseline growth is a separate, pre-existing observation and is listed under the open items below.

*Found by the same change: a TTL was silently dropped on conversion.* TTL is carried by the object's class (§5), and `FromFields` builds the non-TTL twin, so an expiring hash became permanent the moment it converted. `MaybeConvertHashToPaged` re-applies the source's deadline through `AddTTL`. Proven with a negative control — with the branch disabled, `TTL` goes `10000` → `-1` across conversion; with it, `10000` → `10000`, content intact. Both behaviors are locked by `tests/unit_cc/paged_conversion_policy.py`.

**Internal page rows leaked into `KEYS`/`SCAN` — fixed.** Page rows share the object table's keyspace, and the store-scan backfill (`BackfillForScanNextBatch`) had no filter: it treated every returned row as a Redis key and read its first value byte as an object type tag. After a checkpoint, `KEYS *` returned binary `\x00EKVPAGE…` keys, and `SCAN TYPE list` returned hash **pages** because page layout version 1 has the same byte value as the serialized List tag. Both branches (local and remote) now discard magic-carrying keys before pattern/type processing.

Placement matters and is deliberate: the filter is at the point of CONSUMPTION, not at collection (`FetchBucketDataCc::AddDataItem`), because the scan's pagination cursor is the last raw row of the batch — filtering at ingress would leave an all-page-rows batch empty and stall the cursor instead of advancing past it. Measured against a deliberately unfiltered build: 32 leaked rows in `KEYS *`/`SCAN` and 32 in `SCAN TYPE list`, versus 0 with the filter, with the three real keys still returned. Guarded by `tests/unit_cc/paged_scan_leak.py`. A separate internal table for page rows would remove the hazard structurally and is the cleaner end state; deferred as a larger catalog change.

*Noticed while testing this, NOT paged-related:* `DBSIZE` counts only resident entries, so it undercounts after any eviction — five plain string keys give `DBSIZE 0` while `KEYS *` correctly returns 5. Pre-existing, out of scope here.

- **`RESTORE ... - **A crash-restart whose replay crosses the conversion threshold hit the new replay-stall `LOG(FATAL)` once** — 37 buffered commands, zero parked drains, zero in-flight fetches, no progress in 32 s. Two things came out of the investigation regardless:

Combined with the pre-existing intermittent replay-tail gap (the `replay_serving_window.py` note: the log's watermark below the version the store holds, reproducing with paging disabled), a rare stall on the RocksDB backend is expected behavior of that gap, not of conversion. Other cross-type commands were probed on a paged hash — TYPE/EXPIRE/PERSIST/TTL/HGETALL are safe (TTL via virtual `AddTTL`/`RemoveTTL`); DUMP was the only crasher.

## Pre-existing engine bug found while building the standby harness (NOT paged-related)

**An idle EloqKV node burns ~1.15 cores per `core_number=2`.** Reproduced on a plain single node with the shipping RocksDB build, fully initialized and answering PING with no client workload, so it is unrelated to paged objects, the standby work, or the EloqStore/S3 setup. It scales with `core_number`, so it is not a runaway loop -- but an idle engine is supposed to park, which makes this a bug rather than the polling design working as intended.

Localised by thread sampling and a gdb stack dump:

- The native `tx_proc_N` threads are at 0.00 cores -- they park correctly.
- Of four `brpc_worker` threads, three are parked (`bthread::TaskGroup::Wait()`, a timed futex wait, and `LogShippingAgent`'s `condition_variable::wait`). ONE is continuously executing txservice code (`std::_Head_base<0ul, txservice::CcShard*>::_M_head`), i.e. the module-mode shard-driving path. That thread shows only ~12 voluntary context switches per second, so it is RUNNING, not waking -- which rules out a timer firing as the cost, even if a timer is what triggers it.

The park mechanism exists and looks right. With `ELOQ_MODULE_ENABLED`, brpc calls `EloqModule::Process(thd_id)` only while `HasTask(thd_id)` is true, and

```
TxProcessor::HasTask  = external_txm_cnt_ > 0 || !TxProcessor::IsIdle()
TxProcessor::IsIdle   = active_tx_cnt_ == 0 && !terminated_ && LocalCcShards::IsIdle(thd_id)
CcShard::IsIdle       = cc_queue_size_ == 0 && low_priority_cc_queue_size_ == 0
                        && lazy_free_queue_size_ == 0
```

So a single leaked counter -- `external_txm_cnt_`, `active_tx_cnt_`, or any of the three shard queue sizes incremented without a matching decrement -- pins one worker forever. `CcShard::Enqueue` increments `cc_queue_size_` before `cc_queue_.enqueue()`, so any path that consumes a request without decrementing drifts it permanently upward.

**Next step:** log those five values per shard once a second on an idle node. Whichever is non-zero names the leak, and the fix follows from finding the enqueue path missing its decrement. This deserves its own investigation and should not be folded into the paged branch.
